# jit-lang v1.0.0 — stable

**1.0.** The public API is frozen and stable. v0.1.0 stood up the scaffold and the quality gates; v0.2.0 built the core — translating an `ir-lang` function to native machine code, placing it in executable memory, and handing back something you can call. This release ratifies that surface as the `1.0` contract: it follows Semantic Versioning, carries no breaking changes before `2.0`, and ships with the full test and benchmark suite verified across Linux, macOS, and Windows.

The public API does not change from `0.2.0` — a function that compiled then compiles identically now. The release adds the stability documentation and one correctness hardening: instruction-cache coherence, so a compiled function runs correctly on ARM64 as well as x86-64.

## What is jit-lang?

jit-lang is the run-it-now end of the `-lang` language-construction family. A front-end parses, type-checks, and lowers a program to the [`ir-lang`](https://docs.rs/ir-lang) intermediate representation; jit-lang compiles that representation to machine code for the host through [Cranelift](https://cranelift.dev), writes it into a guard-flanked region from [`pager-lang`](https://docs.rs/pager-lang), flips the region to read-execute, and returns a callable handle. There is no object file and no separate linker step — the function runs in the same process that built it.

```rust
use jit_lang::compile;
use ir_lang::{Builder, BinOp, Type};

// fn add(a: int, b: int) -> int { a + b }
let mut b = Builder::new("add", &[Type::Int, Type::Int], Type::Int);
let a = b.block_params(b.entry())[0];
let c = b.block_params(b.entry())[1];
let sum = b.bin(BinOp::Add, a, c);
b.ret(Some(sum));

let f = compile(&b.finish()).expect("add is well-formed");

// SAFETY: the signature is `fn(int, int) -> int`, and `f` outlives the call.
let add: extern "C" fn(i64, i64) -> i64 = unsafe { f.entry() };
assert_eq!(add(19, 23), 42);
```

## The 1.0 surface

The frozen contract:

- **The engine** — `Jit` holds a code generator for the host; `Jit::new` builds it and `Jit::compile` lowers an `ir_lang::Function` to runnable code. The free `compile` does both in one call.
- **The result** — `Compiled` owns the executable memory and reports the function as compiled (`name`, `params`, `ret`, `code_len`), exposes the entry pointer (`as_ptr`), and turns it into a callable function pointer with the one `unsafe` method, `entry::<F>()`.
- **The error** — `JitError`, one variant per stage: `InvalidIr`, `Unsupported`, `Codegen`, `Memory`.

`JitError` is `#[non_exhaustive]`, so a future unsupported-feature or code-generation reason that adds a variant is a non-breaking addition. The IR's machine types map onto the host C ABI — `int` to a 64-bit integer, `float` to `f64`, `bool` to a `0`/`1` byte, and a `unit` return to no return value — and the compiled code uses the host C calling convention, which is what `extern "C"` denotes.

## SemVer promise

The crate follows [Semantic Versioning](https://semver.org):

- No documented item is removed or changed in a breaking way within `1.x`; breaking changes wait for `2.0`.
- New functionality is additive and arrives in minor releases. A new `JitError` variant is a minor change.
- The MSRV is Rust `1.94`, the floor the code generator imposes; raising it is a minor change, never a patch.
- Behaviour is part of the contract: a function that compiles today keeps compiling, and a compiled function computes the same result on the same inputs. The set of supported host architectures may grow, never shrink.

The full statement lives in [`docs/API.md`](https://github.com/jamesgober/jit-lang/blob/main/docs/API.md#semver-promise).

## Breaking changes

**None.** `1.0.0` makes no breaking change to the `0.2.0` surface.

## Hardening since 0.2.0

- **Instruction-cache coherence.** Writing machine code into memory and then executing it is only correct once the processor fetches the bytes the write left behind. On x86-64 the instruction and data caches are unified, so this is automatic; on ARM64 they are not, and the instruction cache must be synchronized over the new code first. `place` now does this before returning — a no-op on x86-64, and an instruction-cache flush on ARM64 (`sys_icache_invalidate` on macOS, the compiler runtime's `__clear_cache` elsewhere). This makes the ARM64 support real rather than nominal; x86-64 behaviour is unchanged. pager-lang manages the memory and its protections; synchronizing the instruction cache at the point of execution is the caller's job, and jit-lang is that caller.
- **Stability documentation.** The crate root, `README`, and `docs/API.md` now state the frozen `1.0` surface and the SemVer promise.

The workflow tests, property tests, error-path tests, runnable examples, and Criterion benchmarks shipped with `0.2.0` and carry forward unchanged.

## What's next

The `1.0` surface is stable until `2.0`. Future work is documentation, tests, and internal optimization that does not change the public contract — plus the additive room the design leaves: function calls (compiling a set of mutually-referencing functions), wider machine types as `ir-lang` grows them, and further code-generation back-ends or optimization levels, each a minor release when it lands.
